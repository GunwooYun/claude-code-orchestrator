# Verification Scripts — the contract

**이 디렉터리가 프로젝트와 오케스트레이터 사이의 계약이다.** 스키마가 아니라
파일시스템이 계약이고, **종료 코드가 인터페이스**다.

오케스트레이터는 이 프로젝트가 어떤 언어인지, 어떤 도구를 쓰는지, 명령이 로컬에서
도는지 컨테이너나 원격 장비에서 도는지 **알지 못하며 알 필요도 없다.** 아래 네
이름을 실행하고 종료 코드를 읽는다.

---

## 네 개의 진입점

| 스크립트 | 인자 | 예산 | 언제 실행되는가 |
|---|---|---|---|
| `verify-save` | 파일 경로 하나 | 초 | 파일을 저장할 때 (훅, 조언만) |
| `verify-task` | 없음 (선택: 범위) | ≤5분 | 태스크 하나가 끝날 때마다 |
| `verify-unit` | 없음 (선택: 범위) | 10~60분 | 작업 단위당 한 번 |
| `verify-full` | 없음 (선택: 범위) | 무제한 | CI 또는 사람이 명시적으로. **자동 실행되지 않는다** |

**인자 없이 호출해도 항상 동작해야 한다.** 훅과 스킬은 인자를 넘기지 않는다.
그 위에서 **뒤따르는 인자를 선택적으로 받을 수 있다** — 모노레포에서 패키지
하나만 검사하거나, 사람이 범위를 좁힐 때 쓴다. 인자를 무시하는 구현도 계약을
지킨다. 인자를 받는다면 그 의미를 스크립트 주석에 적는다.

이름은 `.claude/rules/testing.md` 의 티어 이름과 **정확히 일치한다.** 티어와
스크립트 이름이 어긋나면 어느 쪽이 권위인지 알 수 없게 되므로, 티어를 추가하거나
이름을 바꾸려면 양쪽을 같은 커밋에서 바꾼다.

## 종료 코드

```
0        통과. 출력은 선택 — 있으면 참고 정보다(경고, 진행 상황).
0 이외    실패. 사람이 읽을 수 있는 이유를 stdout 또는 stderr 에 출력한다.
```

그 외 규약은 없다. 코드를 더 만들지 않는다 — 계약이 단순할수록 프로젝트마다
올바르게 구현될 확률이 높다.

**종료 코드 0 의 출력은 버리지 않는다.** 경고만 내고 성공하는 도구(eslint 경고,
clippy, deprecation 알림)가 흔하다. 그 출력을 삼키면 호출자가 "깨끗하다"고 잘못
보고한다. 호출자는 **0 이면 참고 정보로, 0 이외면 실패 이유로** 전달한다.

**"해당 없음"은 종료 코드로 표현하지 않는다.** `verify-save` 가 다루지 않는
종류의 파일을 받으면 **0을 반환하고 아무것도 출력하지 않는다.** 이때만 침묵이
계약이다 — 할 말이 없으니 호출자도 아무 말을 하지 않는다.

## 없는 스크립트

**파일이 없으면 "그 티어는 이 프로젝트에 설정되지 않았다"는 뜻이다.** 호출자는
그 사실을 한 줄로 알리고 넘어간다 — 통과로 간주하지 않고, 실패로도 간주하지
않는다. 모든 프로젝트가 네 티어를 다 가질 필요는 없다.

## 스크립트가 책임지는 것

프로젝트 고유의 복잡함은 **전부 스크립트 안에** 둔다. 호출자로 새지 않게 한다.

- **실행 위치** — 로컬 / 컨테이너 / 원격 장비 / 크로스 빌드 환경
- **경로 변환** — 호스트 경로를 실행 환경의 경로로 (`verify-save` 가 받는 인자는
  호스트 경로다)
- **환경 준비** — 가상환경 활성화, 환경 변수, 툴체인 소싱, 인증
- **어떤 파일을 다루는지** — 확장자 판별은 스크립트 안의 분기로. 별도 설정 파일을
  만들지 않는다
- **공통 코드** — 네 스크립트가 같은 래퍼(컨테이너 진입, 툴체인 소싱)를 쓴다면
  `.claude/scripts/_lib.sh` 처럼 **`_` 로 시작하는 파일**이나 `lib/` 하위에 두고
  불러 쓴다. 중복시키지 않는다. `_` 로 시작하지 않는 이름은 진입점으로 오해된다
- **도구 부재 처리** — 도구가 없으면 그 사실을 말하고, 그것이 실패인지 아닌지를
  스크립트가 결정한다

이유는 단순하다. **사람이 손으로 실행하고 디버깅할 수 있어야 한다.**

```sh
.claude/scripts/verify-save path/to/file   # 저장 시점과 똑같이 재현된다
.claude/scripts/verify-task; echo $?       # 게이트를 그대로 재현한다
```

설정 파일에 명령을 적어두는 방식은 이 재현성을 잃는다.

## 요구사항

- **이름은 `verify-<tier>`, 확장자는 선택이다.** 호출자는 확장자 없는 이름을 먼저
  찾고, 없으면 `verify-<tier>.py`, `.sh`, `.ps1`, `.cmd`, `.bat` 을 찾는다. 확장자가
  있으면 그에 맞는 인터프리터로 실행되므로 **실행 권한도 셔뱅도 필요 없다** —
  Windows 처럼 둘 다 없는 환경을 위한 것이다.
- 확장자 없는 파일을 쓸 때는 실행 권한(`chmod +x`)과 셔뱅이 필요하다.
  이식성을 위해 `#!/bin/sh` 를 권하지만, 프로젝트가 정하면 된다
- **파괴적 동작 금지.** 포맷터가 파일을 고치는 것은 허용되지만, 커밋·푸시·배포는
  하지 않는다.
- **원격 실행은 허용된다.** 로컬에서 검증이 불가능한 프로젝트(CI 에서만 테스트가
  가능한 경우)는 이미 올라간 커밋의 실행을 **트리거하거나 결과를 기다릴 수 있다.**
  코드를 푸시하는 것은 여전히 사람의 몫이고 스크립트가 하지 않는다. 기다릴 수 없는
  티어라면 그 티어의 스크립트를 만들지 않는다 — 없는 것이 거짓 통과보다 낫다
- `verify-save` 는 인자가 없거나 파일이 존재하지 않으면 조용히 0을 반환한다
- `verify-full` 은 어떤 훅에서도 호출되지 않는다는 전제로 작성한다

## 누가 이 스크립트를 만드는가

`/initproject` 가 프로젝트당 한 번 만든다. 스택을 감지하고, 실제 명령을 사용자에게
확인한 뒤 작성한다. 이후 프로젝트가 직접 소유하고 수정한다 — 템플릿을 다시
복사해도 덮어쓰지 않는다.

## 누가 호출하는가

| 호출자 | 무엇을 |
|---|---|
| `.claude/hooks/lint-on-save.py` | `verify-save <path>` (조언만, 차단 못 함) |
| `.claude/skills/feature/SKILL.md` 의 "Implementation Loop" | `verify-task`, 마지막에 설정된 가장 느린 티어 |
| `/feature` Phase 2b 검증 계획 | 시나리오의 "명령" 칸에 이 이름들을 쓴다 |
| CI, 또는 `.git/hooks/pre-commit` | `verify-task` 또는 `verify-full` |

## 이 저장소의 구현

이 디렉터리의 스크립트는 **이 저장소 자신의 구현**이다(Python + uv + ruff + ty +
pytest). **다른 프로젝트의 참고 답안이 아니다** — 계약은 위의 네 이름과 종료
코드뿐이고, 그 안을 무엇으로 채우는지는 프로젝트마다 완전히 다르다.

스크립트를 읽을 때 계약(이름·인자·종료 코드)과 구현(어떤 도구를 부르는지)을
구분해서 본다.
