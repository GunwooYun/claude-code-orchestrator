# Writing Style — 문서 작성 규칙

사용자가 정의한 문서 작성 규칙이다. `.claude/rules/writing-style.md`가 이 파일을
가리킨다. 문서·보고서·티켓 본문을 쓰기 전에 **먼저 읽는다.**

**우선순위**: 아래쪽 장이 위쪽을 덮어쓴다. **9장(예외 규칙)이 최우선이고,
사실이 불확실할 때는 3.4(미확정 처리)가 다른 모든 규칙을 앞선다.**

---

## 1. 적용 범위

### 1.1 대상 문서

```
- 기술 검토·의사결정 보고서 (Confluence)   ← 기본형. 4.1의 골격이 이것 기준
- 단계별 학습/인수인계 문서 (Confluence)
- Jira 티켓 본문 (프로젝트별 기존 템플릿에 맞춰 채움)
- 저장소 내 준거/감사 문서 (docker/fips/*.md 류)
- 구현 계획서 (저장소 jobs/<티켓>/plan.md)
```

티켓 본문은 **기존 템플릿의 섹션 제목을 바꾸지 않는다.** 그 안을 채울 뿐이다.

### 1.2 독자

**해당 도메인을 모르는 같은 회사 엔지니어**를 기본 독자로 둔다. 그 사람이
1장만 읽고도 나머지를 따라올 수 있어야 한다.

부차 독자가 둘 더 있고, 둘 다 문서 구조에 영향을 준다.
- **결정권자**: 요약과 결론만 읽는다 → 요약에 결정·근거·영향이 다 있어야 한다
- **외부 심사자/감사자**(준거 문서에 한함): 적대적으로 읽는다 → 검증하지 않은
  문장이 하나라도 있으면 문서 전체가 의심받는다

### 1.3 문서가 남는 이유

**나중에 이 결정을 뒤집어야 할 때 근거를 찾기 위해서.**

그래서 "무엇을 했다"보다 **"무엇을 몰랐고 무엇을 감수했는가"**가 중요하다.
잘 된 부분은 코드가 증명하지만, 감수한 대가는 문서에만 남는다.

## 2. 언어

### 2.1 본문 언어

본문은 **한국어**. 아래는 원문 유지.
- 기술 용어, 클래스·함수·파일·명령어·식별자
- 규격/조항 인용문 (번역하면 인용이 아니게 된다)
- 코드 블록과 도식 내부 전체

조항이나 표준 문서를 인용할 때는 **원문 그대로** 싣고, 필요하면 아래에 해설을
붙인다. 번역본만 싣지 않는다.

### 2.2 문체

**합니다체**("~합니다", "~입니다"). 사용자에게 보고하는 문서이므로 평서체로
쓰지 않는다.

예외 둘:
- **표 안, 도식 안, 체크리스트**는 종결어미 없이 명사형/개조식
- **저장소 안의 영문 문서·주석**은 영어 평서체 (`docker/fips/*.md` 등)

### 2.3 용어 표기

```
영어 유지: build, gate, assertion, provider, digest, manifest, fallback,
          rollback, stage, pipeline, provenance
한글 고정: 단정(assertion을 문장에서 쓸 때), 판별식, 함정, 증거, 경계
금지: "어썰션"(X) → 단정 또는 assertion
      "체크"(X) → 검사 / 확인 / 단정 중 정확한 것
```

**"검증"과 "확인"과 "단정"을 구분한다.** 출력만 하는 것은 확인도 아니고,
실패 시 중단되는 것만 단정이다.

### 2.4 약어

업계 표준 약어(API, DB, CI, TLS, CVE)는 그냥 쓴다.

**인증서 번호·조항 번호는 첫 등장 시 무엇인지 한 번 밝힌다** —
`CMVP #4985`, `CMVP Management Manual §7.9.2 각주 5` 처럼 매번 정확히 쓰고
"그 조항"으로 뭉뚱그리지 않는다. 나중에 조항 번호가 틀리면 문서 전체가 흔들린다.

## 3. 구성 원칙

### 3.1 결론의 위치

**결론 먼저.** 문서 맨 위에 `요약` 섹션을 두고 그 안에:
1. 한 문장 결론 (굵게)
2. 비교 표 — 현행 유지 vs 제안, 3~6행
3. 이 문서에서 다룰 것 예고 (패널)

예: *"검토 결과: 다운그레이드를 권고하지 않습니다."* 를 첫 줄에 두고,
근거는 2장 이후에.

**권고와 반대되는 결정을 상정한 섹션을 반드시 둔다** — "그래도 진행한다면".
결정권자는 문서와 다른 선택을 할 수 있고, 그때 무엇을 해야 하는지가 없으면
문서가 쓸모를 잃는다.

### 3.2 분량

상한을 두지 않는다. 대신 **장마다 독립적으로 읽히는지**로 판단한다.

- 1장(배경)은 도메인을 모르는 독자가 읽고 나머지를 따라올 수 있는 최소량
- 한 장이 화면 3개를 넘어가면 하위 장으로 쪼갠다
- 단계별 문서는 **phase 당 한 페이지**, Confluence 하위 페이지로 분리

분량보다 **중복이 없는지**가 기준이다. 같은 사실을 두 곳에서 말하면 반드시
어긋난다.

### 3.3 근거의 밀도

**채택한 안과 탈락한 안을 같은 밀도로 쓴다.**

핵심 규칙: **반대 논거를 의도적으로 강화해서(steelman) 찾은 뒤 각각 반박한다.**
별도 리서치를 돌려서라도 찬성 논거를 적극적으로 수집하고, 원문 인용 형태로
그대로 실은 뒤 반박을 붙인다. 반박하지 못하면 그렇게 적는다.

각 논거에 **판정을 붙인다**: `정확함` / `부분 인정` / `근거 없음` /
`성립하지 않음` / `판단에서 제외`.

근거의 **신뢰도도 문서에 쓴다**. 예:
> 이 논거는 조항 원문 인용이 없고 우리 제품이 그 인증 경로에 있다는 근거도
> 없어 **판단에서 제외했습니다.**

### 3.4 미확정 사항 (사실이 불확실할 때 최우선 규칙)

추측으로 채우지 않는다. 대신 **무엇을 확인했고 무엇을 못 했는지 명시**한다.

```
[확인함]    원문/실측으로 검증. 출처나 측정 방법을 함께
[추론]      근거는 있으나 직접 확인하지 않음. 추론 방법과 한계를 명시
[미확인]    확인하지 못함. 왜 못 했는지와 누가 무엇을 하면 되는지
```

**측정하지 못한 것을 측정한 것처럼 쓰지 않는다.** 확인 수단이 막혔으면
("EUR-Lex 가 자동 접근을 차단함") 그 사실 자체를 적고, 사람이 해야 할 일을
남긴다.

## 4. 문서 골격

### 4.1 기술 검토·의사결정 보고서 (기본형)

```
요약
  - 한 문장 결론(굵게) + 비교 표 + 다룰 내용 예고 패널
1. 배경 — 먼저 알아야 할 것
  - "이 문서는 ~를 모르는 분도 읽을 수 있게 작성했습니다" 로 시작
  - 1-1 개념: 도식 + 비유 1개
  - 1-2 무엇이 쟁점인가: 경계·구분을 세움
  - 1-3 현재 구조: 도식
2. 제안 내용
  - 제시된 근거를 번호로 나열 + 각각의 검토 결과 표
3. 찬성 근거 (외부 리서치)
  - 논거마다: 인용 → 판정 → 반박
4. 반대 근거
5. 핵심 — 이 문서의 결정적 논점 하나
  - 타임라인·흐름 도식
6. 우리 제품에 미치는 영향
  - 노출 경로, 실측값
7. 구조적 문제 — 이 선택이 유지되지 않는 이유
8. 결론 및 권고
  - 판단 기준 표 + "그래도 진행한다면" + 함께 해야 할 일 + 대안
부록 — 조사 방법 및 출처
  - 조사 방법, 신뢰도 기록, 출처 링크, 관련 티켓
```

### 4.1b 단계별 학습/인수인계 문서

```
요약 — 변경 표 + "이 문서의 줄기" 패널(번호 목록)
1. 배경 — 이번 단계가 건드리는 것 (도식 + 사고 사례)
2~N. 각 발견을 한 장씩
  - 각 장은 "무엇을 믿었나 → 실제 → 어떻게 드러났나" 로 전개
N+1. 이번 단계에서 배운 것
  - 표: 믿고 있던 것 / 실제 / 어떻게 드러났나
  - 패턴을 일반화하는 패널 1개
커밋 / 다음 단계 / 참고
```

### 4.1c 준거·감사 문서 (저장소)

```
0. 선언부 — 심사자용, 자족적
   0.1 이 문서 형식의 근거 (왜 이 구조인지, 무엇을 주장하지 않는지)
   0.2 발급자   0.3 대상(추적 가능한 수준까지)   0.4 선언문 + 필수 캐비엇
   0.5 조건과 충족 방법 (증거 ID 연결)
   0.6 유사 제도와의 관계
   0.7 증거 등록부 (ID / 뒷받침하는 주장 / 산출물 / 검증 방법)
   0.8 재현 절차 (실행 가능한 명령)
   0.9 주장하지 않는 것   ← 서명 앞에 둔다
   0.10 무효화 조건   0.11 발행·서명
1~N. 엔지니어링 근거 (다음에 코드를 고칠 사람용)
```

### 4.2 항상 / 절대

```
항상:
  - 관련 Jira 티켓 링크, 저장소 경로(파일:줄 번호까지)
  - 실측값은 실제 출력 그대로 (재구성 금지)
  - 상위/형제 문서 링크 (연작이면)
  - 조사 방법과 신뢰도 (외부 리서치를 썼다면)

절대 금지:
  - 검증하지 않은 조항·수치·인용
  - 스크린샷으로 대체한 표나 로그 (텍스트로)
  - "~로 보인다"를 "~이다"로 쓰기
  - 이전 개정판의 오류를 조용히 지우기 → 무엇이 틀렸는지 남긴다
```

## 5. 서식

### 5.1 제목 레벨

H1은 장 제목으로 쓴다(Confluence 본문에서 H1 사용 허용).
장 → `#`, 절 → `##`, 항 → `###`. **H4 이상 금지.**

장과 장 사이에 `---`(수평선)을 넣어 시각적으로 끊는다.

### 5.2 표 / 도식 / 문단 / 목록

```
표      3개 이상 항목을 2개 이상 속성으로 비교할 때. 판정·대조·매핑
도식    구조, 경계, 흐름, 타임라인, 의사결정. 코드블록 안 ASCII
문단    인과관계와 논증. "왜"는 문단으로 쓴다
목록    순서가 있거나 체크리스트일 때만
```

**불릿으로 논증하지 않는다.** 불릿은 열거이고, 논증은 문단이다.
**표를 만든 뒤 같은 내용을 문장으로 반복하지 않는다.**

도식은 비유와 함께 쓴다 — 경계 개념은 `금고 / 금고를 둘러싼 건물`처럼
물리적 비유가 붙으면 한 번에 전달된다.

### 5.3 강조·코드·링크

```
**굵게**   문단당 1~2회. 그 문단에서 하나만 기억한다면 이것, 인 부분
`인라인`   파일명·명령어·식별자·버전·해시·조항 번호
인용문     규격 원문, 이전 개정판의 오류, 다른 사람의 주장
```

링크는 대상 이름으로. **해시·버전·경로는 반드시 인라인 코드**로 감싼다 —
맨 텍스트로 두면 나중에 검색이 안 된다.

### 5.4 도식

**텍스트 도식(ASCII)을 기본으로 한다.** 코드블록 안에 넣는다.

이유: Confluence·Markdown·터미널·Jira 어디서나 같게 보이고, diff 가 되고,
수정이 가능하다. 이미지는 수정이 안 되므로 금지.

```
경계도      무엇이 안이고 무엇이 밖인가          → 1장
대조도      [변경 전] / [변경 후] 나란히          → 요약, 변경 설명
흐름도      A → B → C, 분기와 실패 경로           → 영향 분석
타임라인    ====X 로 종료 시점 표시                → 지원 기간, 만료
결정 트리   선택지와 각각의 귀결                   → 결론부
```

Mermaid 는 쓰지 않는다 — 렌더링 환경에 의존한다.

## 6. Confluence

### 6.1 페이지 제목

연작이 아닌 단일 보고서: `<대상> <행위> Report`
예: `OpenSSL 3.5.8 -> 3.1.2 Downgrade Report`

연작(단계별 문서): 부모 페이지를 티켓 키로 만들고 하위에
`Phase <n>-<m> — <그 단계의 주제>`
예: `Phase 3-4 — 검증 게이트 재작성과 고정 모듈 해시`

**제목에 결론을 넣지 않는다.** 제목은 대상을 말하고, 결론은 첫 줄에서 말한다.

### 6.2 위치와 라벨

티켓 단위 연작은 **티켓 키로 부모 페이지를 만들고 그 하위에** 단계별 페이지를
쌓는다. 부모 페이지는 비어 있어도 된다 — 목차 역할.

단일 보고서는 지시받은 스페이스 최상위.

**생성 위치를 임의로 정하지 않는다.** 정해지지 않았으면 묻는다.

### 6.3 매크로

```
panel-info      이 문서의 줄기, 일반화된 교훈, 방법론 설명
panel-note      단서, 정직한 부연, "정확히 말하면"
panel-warning   감수하는 대가, 주의해야 할 함정, 하면 안 되는 것
panel-success   확정된 좋은 결과, 실측으로 확인된 사실
panel-error     사고 사례, 거짓 통과, 지금 깨져 있는 것
```

**패널 안에 표를 넣을 수 없다**(ADF 제약). 표가 필요하면 패널 밖으로.

작성은 **storage format(XHTML) 로 직접** 한다. Markdown 변환에 의존하지 않는다.
코드블록 안의 `<`, `&` 는 `&lt;`, `&amp;` 로 이스케이프한다.

목차 매크로는 쓰지 않는다 — 장 구조가 이미 목차 역할을 한다.

### 6.4 발행 정책

**새 페이지는 발행해도 된다.** 단, 발행 직후 링크와 함께 무엇을 어떤 구조로
썼는지 보고한다.

**기존 페이지 수정은 반드시 먼저 확인받는다.** 다른 사람이 읽고 있을 수 있다.

**발행 위치가 정해지지 않았으면 묻는다.**

사실이 나중에 정정되면 **해당 페이지도 정정한다.** 커밋 해시처럼 바뀔 수 있는
값을 본문에 썼다면 특히.

## 7. 발행 전 체크리스트

```
[사실]
- [ ] 모든 수치·해시·버전·조항 번호를 실제 대상과 대조했는가
- [ ] 문서에 적은 명령을 그대로 실행해 봤는가
- [ ] "측정했다"고 쓴 것을 실제로 측정했는가
      (캐시 적중을 재현으로 착각하지 않았는가)
- [ ] 추론과 확인을 구분해서 표기했는가
- [ ] 외부 리서치 결과를 1차 출처와 대조했는가

[구조]
- [ ] 첫 줄에 결론이 있는가
- [ ] 1장만 읽고 도메인을 모르는 독자가 따라올 수 있는가
- [ ] 반대 논거를 강화해서 다뤘는가
- [ ] 감수하는 대가가 명시되어 있는가
- [ ] 권고와 반대되는 선택을 상정한 섹션이 있는가

[정직성]
- [ ] 이전에 내가 틀리게 쓴 것을 조용히 지우지 않고 정정으로 남겼는가
- [ ] 이 문서가 주장하지 않는 것을 적었는가 (준거 문서 필수)
- [ ] 확인 못 한 것을 확인한 것처럼 쓰지 않았는가

[중복]
- [ ] 같은 사실을 두 곳에서 말하고 있지 않은가
- [ ] 표 아래에 같은 내용을 문장으로 반복하지 않았는가
```

## 8. 안티패턴

```
[도입·분량]
- 내용 없는 도입부 금지. 첫 문장이 결론이거나 대상이어야 한다
- "본 문서에서는 ~에 대해 살펴본다" 류 금지
- 이모지 금지 (본문. 체크표시는 표 안에서만 허용)
- 강조 부사 금지: 매우, 굉장히, 혁신적인, 획기적인

[확실성]
- 확인 안 된 것을 단정하지 말 것 — "~로 보인다"와 "~이다"를 구분
- 조항 번호·CVE 번호·해시를 기억으로 쓰지 말 것. 원문 대조 없으면 쓰지 말 것
- 외부 리서치 결과를 그대로 옮기지 말 것. 검증하거나 미검증임을 명시
- "테스트했다"를 양성 시험만 하고 쓰지 말 것
  — 실패해야 할 때 실패하는지 확인

[구조]
- 불릿 3단 이상 중첩 금지
- 불릿으로 논증하지 말 것 (논증은 문단)
- 표를 만들고 바로 아래 같은 내용을 문장으로 반복하지 말 것
- 한 문장에 쉼표 3개 이상 금지
- 같은 사실을 두 문서에 쓰지 말 것 — 한쪽을 참조로

[정직성 — 가장 중요]
- 내 이전 진술이 틀렸으면 조용히 고치지 말 것. 무엇이 왜 틀렸는지 남길 것
- 문서가 할 수 없는 것을 흐리지 말 것. 한계를 먼저 쓸 것
- 좋게 들리는 요약으로 나쁜 사실을 덮지 말 것
- 성공 로그만 보고 "통과"라고 쓰지 말 것 — 출력은 검증이 아니다
```

## 10. 기준 문서와 암묵적 패턴

**기준 문서**: https://auto-jira.atlassian.net/wiki/x/PIA_wg
`OpenSSL 3.5.8 -> 3.1.2 Downgrade Report`

규칙으로 적기 어려운 암묵적 패턴:

1. **1장 전체를 배경에 쓴다.** 판단이 걸려 있는 개념 하나를 도식과 비유로 세운
   뒤, 나머지 장이 전부 그 개념 위에서 전개된다.
   → *"인증받은 건 안쪽 상자 하나뿐 → 취약점은 거의 전부 바깥에서 나온다"*

2. **반대 논거를 내가 대신 강화해서 가져온다.** 별도 리서치를 "찬성 논리를
   의도적으로 강화해서" 한 번 더 돌리고, 나온 논거를 원문 인용으로 싣고
   각각 반박한다. 반박 못 하는 건 "부분 인정"으로 적는다.

3. **근거의 신뢰도를 문서에 남긴다.**
   → *"조항 원문 인용이 없어 판단에서 제외했습니다"*
   → *"가장 강해 보였던 논거가 1차 자료와 정면 충돌해 성립하지 않음을 확인"*

4. **결론과 반대되는 선택을 위한 섹션을 둔다.** "그래도 진행한다면" +
   그 경우 반드시 함께 해야 할 일 체크리스트.

5. **사유를 정확히 기록하라고 요구한다.**
   → *"안정성을 위해"가 아니라 "빌드 단순화를 위해 보안 패치 수신을 포기한다"로
   기록해야 합니다*

6. **구조적 논점을 따로 한 장으로 세운다.** 개별 장단점이 아니라
   "이 선택은 유지되지 않는다"는 형태의 논점.

**연작 예시**: https://auto-jira.atlassian.net/wiki/x/AoCBwg (Phase 1-2),
https://auto-jira.atlassian.net/wiki/x/AwCCwg (Phase 3-4)
— 마지막 장을 "이번 단계에서 배운 것" 표로 닫는 형식.

### 나쁜 예시 (사용자 본인이 쓰고 정정한 문장들)

```
[나쁨]  "module-mac 이 8/31 기록과 일치하므로 재현된다"
[문제]  캐시 적중이었다. 빌드 로그의 CACHED 줄을 안 봤다
[좋음]  "--no-cache 재빌드에서 CACHED 0건, 같은 해시. 비트 단위로 재현된다"

[나쁨]  "Stage B 의 비인증 모듈을 Stage A 의 것으로 덮어쓴다"
[문제]  소스를 안 봤다. install_sw 는 fips 모듈을 설치조차 하지 않는다
[좋음]  "비인증 모듈이 모듈 디렉터리에 들어온 적이 한 번도 없다" (더 강한 사실)

[나쁨]  "이제 module-mac 만이 둘을 구별한다"
[문제]  측정 안 하고 썼다. 바이트가 동일해서 MAC 으로도 구별 안 된다
[좋음]  "구별되는 것은 출처뿐이고, 출처는 산출물에서 관측할 수 없다"

[나쁨]  "두 버전이 같아지면 두 소스 빌드가 붕괴된 것이다"
[문제]  원래 근거가 없는 판별식이었는데 단정형으로 썼다
[좋음]  "그 테스트는 애초에 부당했고 철회한다" + 무엇이 실제 판별인지

[나쁨]  "음성 시험 확인 — 구 이미지는 막히고 새 이미지는 통과"
[문제]  로직만 따로 돌렸다. 스크립트로 돌렸으면 첫 줄에서 죽었다
[좋음]  실제 실행 경로에서 확인한 뒤에 쓴다
```

**공통 패턴**: 다섯 건 모두 **"통과하는 방향"으로 틀렸다.** 실패하는 방향으로
틀렸으면 즉시 드러났을 것이다. 그래서 8장의 *"성공 로그만 보고 통과라고 쓰지
말 것"* 이 가장 중요한 항목이다.
