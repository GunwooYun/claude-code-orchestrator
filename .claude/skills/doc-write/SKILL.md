# Document Writing

**사용자가 정의한 스타일 규칙으로 문서를 쓴다.**

이 스킬은 **절차**를 담당한다. 스타일 규칙 자체는
`.claude/docs/writing-style.md` 에 있고, 여기에 복사하지 않는다 — 두 곳에 같은
규칙이 있으면 반드시 어긋난다.

## 발동 경계

| 발동한다 | 발동하지 않는다 |
|---|---|
| Confluence 링크 + 작성/수정 요청 | "설명해줘", "분석해줘", "요약해줘" → **채팅 답변** |
| "문서로 정리해줘", "보고서 써줘", "페이지 만들어줘" | 코드 주석·docstring·커밋 메시지 |
| Jira 티켓 본문 작성 | 작업 결과를 사용자에게 보고하는 것 |
| 저장소 준거·감사 문서, `jobs/<티켓>/plan.md` | 계획·비교·정리를 채팅으로 요청 |

**애매하면 채팅으로 답하고 "문서로 만들까요?"를 한 줄 붙인다.** 원치 않는 페이지가
생기는 것보다 한 줄 묻는 것이 싸다.

---

## Step 1 — 스타일 규칙을 먼저 읽는다

```
Read .claude/docs/writing-style.md
```

**기억으로 쓰지 않는다.** 466줄이고, 문서 종류별 골격(§4.1), 패널 용도(§6.3),
발행 정책(§6.4), 발행 전 체크리스트(§7), 안티패턴(§8)이 거기 있다.

우선순위: **§9 예외 규칙이 다른 모든 장을 덮어쓰고, 사실이 불확실하면 §3.4가
구조·서식 규칙 전부를 앞선다.**

## Step 2 — 문서 종류와 목적지를 확정한다

| 종류 | 목적지 | 골격 |
|---|---|---|
| 기술 검토·의사결정 보고서 | Confluence | §4.1 (기본형) |
| 단계별 학습/인수인계 | Confluence, 연작 하위 페이지 | §4.1b |
| 준거·감사 문서 | **저장소** (`docker/fips/*.md` 류) | §4.1c, **영어 평서체**(§9-1) |
| 구현 계획서 | **저장소** `jobs/<티켓>/plan.md` | 프로젝트 관례 |
| Jira 티켓 본문 | Jira | **기존 템플릿 섹션을 그대로**(§9-2) — 제목을 바꾸지 않는다 |

저장소 문서는 Confluence 를 거치지 않는다. 파일로 쓰고 커밋 대상에 올린다.

## Step 3 — Confluence 인 경우: 연결과 위치를 확인한다

### 3a. 연결 확인

Atlassian MCP 도구로 먼저 확인한다 — **도구 이름은 커넥터 설정에 따라 다르므로
이 세션에 실제로 있는 이름을 쓴다** (`atlassianUserInfo` /
`getAccessibleAtlassianResources` 계열).

- 도구가 없거나 인증되지 않았으면 **거기서 멈춘다.** 사용자에게 커넥터 연결이
  필요하다고 알린다. **로그인은 대신 할 수 없다** — OAuth 흐름은 클라이언트에서
  사용자가 직접 한다.
- 초안을 이미 썼다면 버리지 않고 채팅에 제시한다. 연결 문제로 작업이 사라지면 안
  된다.

### 3b. 위치는 묻는다

**스페이스 키와 부모 페이지는 이 프로젝트에 정해져 있지 않다.** §6.2 가
"생성 위치를 임의로 정하지 않는다. 정해지지 않았으면 묻는다"고 규정한다.

한 번에 묻는다 (AskUserQuestion 하나로):

1. **스페이스** — 어느 스페이스인가
2. **부모 페이지** — 최상위인가, 특정 페이지 하위인가
3. **연작 여부** — 단일 보고서인가, 티켓 키 부모 아래 단계별 페이지인가

답을 받으면 **이 스킬 파일이 아니라 `CLAUDE.md` 의 `## Current Project` 에
기록한다** — 프로젝트별 값이므로 템플릿에 박으면 다음 프로젝트에서 틀린다.
기록해 두면 다음부터 묻지 않는다.

### 3c. 제목과 라벨

§6.1 을 따른다. 요약하면:

- 단일: `<대상> <행위> Report`
- 연작: 부모를 티켓 키로, 하위를 `Phase <n>-<m> — <주제>`
- **제목에 결론을 넣지 않는다.** 제목은 대상을, 결론은 첫 줄을 담당한다.

## Step 4 — 초안을 쓴다

§4 의 골격을 순서대로 채운다. 매번 틀리는 지점만 다시 적으면:

- **첫 줄이 결론**(§3.1). 한 문장 결론(굵게) → 비교 표 → 다룰 내용 예고 패널
- **"그래도 진행한다면" 섹션을 반드시 둔다**(§3.1) — 결정권자가 문서와 다른
  선택을 할 수 있다
- **반대 논거를 의도적으로 강화(steelman)해서 가져온 뒤 각각 반박**하고,
  논거마다 판정을 붙인다: `정확함` / `부분 인정` / `근거 없음` / `성립하지 않음` /
  `판단에서 제외` (§3.3)
- **[확인함] / [추론] / [미확인]** 을 구분해 표기한다(§3.4)
- 도식은 **코드블록 안 ASCII**. Mermaid 와 이미지는 쓰지 않는다(§5.4)
- **불릿으로 논증하지 않는다.** 논증은 문단이다(§5.2)

### Confluence storage format

**storage format(XHTML)으로 직접 쓴다.** Markdown 변환에 의존하지 않는다(§6.3).

- 이 세션에 포맷 가이드 도구가 있으면(`getContentFormatGuide` 계열) **쓰기 전에
  호출한다.** 매크로 구조를 기억으로 쓰면 깨진다.
- 코드블록 안의 `<`, `&` 는 `&lt;`, `&amp;` 로 이스케이프한다
- **패널 안에 표를 넣을 수 없다**(ADF 제약). 표가 필요하면 패널 밖으로
- 패널 종류는 §6.3 의 용도 표를 따른다
- 목차 매크로는 쓰지 않는다

## Step 5 — 발행 전 자가 점검

§7 의 체크리스트를 **항목별로 실제로 확인한다.** 넷으로 묶여 있다 — 사실 / 구조 /
정직성 / 중복.

특히 이 세 가지는 통과 여부를 말로 확인한다:

- **문서에 적은 명령을 그대로 실행해 봤는가** — 안 해봤으면 [추론]으로 표기
- **"측정했다"고 쓴 것을 실제로 측정했는가** — 캐시 적중을 재현으로 착각하지 않았는가
- **이전에 내가 틀리게 쓴 것을 조용히 지우지 않고 정정으로 남겼는가**

체크리스트를 통과하지 못하는 항목이 있으면 **발행하지 않고** 그 항목을 먼저
해결하거나 [미확인]으로 명시한다.

## Step 6 — 발행

§6.4 의 정책을 그대로 따른다.

| 상황 | 동작 |
|---|---|
| **새 페이지** | **발행해도 된다.** 발행 직후 **링크와 함께 무엇을 어떤 구조로 썼는지 보고**한다 |
| **기존 페이지 수정** | **반드시 먼저 확인받는다.** 다른 사람이 읽고 있을 수 있다. 변경안을 제시하고 승인을 받은 뒤 수정 |
| **위치 미정** | 묻는다. 임의로 정하지 않는다 |
| **저장소 문서** | 파일로 쓰고, 커밋은 프로젝트의 커밋 정책을 따른다 |

발행 후:

- **사실이 나중에 정정되면 해당 페이지도 정정한다**(§6.4). 커밋 해시처럼 바뀔 수
  있는 값을 본문에 썼다면 특히
- 연작이면 상위·형제 페이지 링크를 서로 연결한다(§4.2)

## 실패 모드

이 스킬이 조용히 잘못되는 방식들이다.

- **스타일 문서를 안 읽고 기억으로 쓴다** → 골격이 어긋나고 패널 용도가 섞인다.
  Step 1 을 건너뛰지 않는다.
- **위치를 추측해서 발행한다** → 엉뚱한 스페이스에 페이지가 생긴다. 모르면 묻는다.
- **기존 페이지를 확인 없이 고친다** → 되돌리기 어렵고 남의 작업을 덮는다.
- **체크리스트를 형식적으로 통과시킨다** → §8 의 "정직성" 항목이 무의미해진다.
  확인하지 않은 것은 [미확인]으로 남긴다.
- **채팅 답변이면 되는 요청에 문서를 만든다** → 발동 경계를 다시 본다.

→ 스타일 규칙 전문: `.claude/docs/writing-style.md`
→ 항상 적용되는 정직성 규칙: `.claude/rules/writing-style.md`
